架构与调用流程¶

当前系统如何工作¶

flowchart LR
    CLI[CLI操作入口] --> S[services业务编排]
    CLI --> Q[jobs任务队列]
    Q --> W[worker与handlers]
    W --> S
    S --> A[analysis解析与持仓规则]
    A --> R[SourceRouter与来源协议]
    S --> R
    R --> H[HTTP/限流/免费额度/适配器]
    S --> D[(PostgreSQL)]
    Q --> D

查询可以直接读取已存结果；采集则通过队列与路由，产生可追溯的状态和证据。REST、关联信号、聚类及报表的目标架构不等于当前存在的运行入口。

一条功能如何追踪¶

以持仓为例，先从使用方法确认读取已有快照；沿页面进入实现时序、HolderService、snapshot/holders表，再到存储测试和ADR。站点的目录结构按读者问题排列，源码仍保留现有目录组织。

层 当前职责 入口
输出 参数、输出、退出码 cli.py
业务 查询/采集编排、事务、身份与标签 services/
任务 队列领取、worker、处理器和状态 jobs/
解析与规则 部署者、类型、持仓覆盖、标签优先级 analysis/
适配与基础设施 来源协议、HTTP、重试、路由、限流/额度 sources/、core/
数据与模型 ORM、迁移、统一领域模型 db/、models/、migrations/

为什么按层拆分¶

来源适配器不写业务库；命令与任务复用services；分析依赖路由协议，不直接散落HTTP请求；表和统一模型减少不同链/来源字段差异。当前使用Python＋PostgreSQL单机，队列也存PG，避免额外Redis/Celery运维。

未来重量级关联信号选择本机SQL，旧Dune方案已被替代，不能按历史ADR-004重新接入。依据：ADR-001、ADR-002、ADR-006、ADR-014。
