持仓快照¶

如何使用：查询已有持仓¶

uv run python -m aitrade --json holders show 999

把999换成已有UCID。它读取这个UCID各支持链/合约已经保存的最新快照，按rank列出持仓，不向链上重新请求。

“最新”是数据库中is_latest=true，不是“此刻链上余额”。每次保存的是一次观察快照，taken_at是记录时间；block_number只在来源有证据时填写，不能仅凭分页结束认定同区块一致。

如何读结果¶

下面为合成示例，按M3 CLI测试Fixture的UCID999、ethereum、100/1000余额场景构造；时间和ID仅用于说明，未执行生产命令。

{
  "ucid": 999,
  "snapshots": [{
    "snapshot_id": 1,
    "chain": "ethereum",
    "address": "0xcccccccccccccccccccccccccccccccccccccccc",
    "source": "blockscout",
    "status": "complete",
    "partial_reason": null,
    "taken_at": "2026-10-29T00:00:00+00:00",
    "holders": [{
      "rank": 1,
      "node_id": "ethereum:0xaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "balance_raw": "100",
      "pct": 0.1
    }]
  }]
}
字段 含义
snapshot_id / taken_at 哪次已存观察及记录时间；比较快照使用ID
status / partial_reason complete或partial；partial必须保留原因，不等于已证明完整Top500
balance_raw 原始整数余额，JSON字符串避免精度丢失；人类数量需按decimals换算
pct balance_raw / total_supply_raw，0.1表示10%，不是0.1%；未知供应量时可为null
node_id 当前保存的节点身份；同地址跨链可能有不同身份，见下文

show只展示有限的字段，不包含快照表全部字段；供应量、decimals、来源区块等可通过限定快照的SQL查看。JSON便于完整表达链、快照、列表和null；本命令没有额外的人类表格模式。

两次观察如何比较¶

uv run python -m aitrade holders diff 1 2

以上ID同样是合成示例。两次必须属于同一合约；仅两边都出现的地址才计算余额差。跌出TopN只表示“不在这次榜单”，不能直接推断归零。全部参数。

如何实现¶

查询：CLI → holder_snapshots关联token_contracts（UCID）→ 仅选is_latest → holders按rank读取。

采集保存是另一条需授权的工作流：jobs enqueue holders → worker → HolderService.collect → 生产来源 → 单事务保存快照/持仓/随行标签/画像任务。不是打开网站或show命令时发生。

sequenceDiagram
    participant U as 操作者
    participant C as CLI
    participant D as PostgreSQL
    U->>C: holders show UCID
    C->>D: 按UCID查各合约最新已存快照
    D-->>C: 快照及rank排序的holders
    C-->>U: JSON（不重新采集）

为什么这样设计¶

历史余额与供应量随快照冻结，latest只是每个合约的当前选择；保留多次观察才能比较。陌生EVM持仓先以链节点记录，仅当前链有效代码证据才支持复用全局EOA，已知链合约优先。读取不偷偷更正历史；正式数据影响审计与修复另行授权。

依据：ADR-039（M3实现）、ADR-063（有效覆盖与完整率分列）、ADR-136（当前链身份与标签事务）。
