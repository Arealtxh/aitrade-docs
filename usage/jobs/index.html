任务与状态¶

如何使用：查看，而不是执行¶

uv run python -m aitrade status
uv run python -m aitrade jobs list --kind holders --limit 20

status展示任务统计、常见错误与额度快照；额度中的key_hash是标识，不是原API key。list显示逐任务状态、尝试与last_error；不要把错误或配置原文复制到公开位置。

状态 解释
pending 已排队，尚未被worker领取
running 被worker持有，心跳用于识别卡住任务
done 此任务处理完成；不能单凭它证明业务质量或覆盖率
partial 有可用部分或结果未能完整确认，仍需看原因和对应验收
failed 本次失败，保留失败类型/尝试，不冒充来源不存在

写入或运行入口¶

  • jobs enqueue：目前支持deployer、holders、address_profile；写队列，不代表已经拿到结果。--with-funding仅用于画像任务。
  • jobs run：启动worker并可能请求外部来源/写库；默认持续运行，--until-empty在没有可立即领取的任务时退出；退避中的pending仍可保留，退出不证明队列已清空。--max-minutes限制单轮时间。
  • jobs retry：改变匹配状态的任务，使其重新入队；源码接受JobStatus中的状态，不应随意重置done或running任务。

这些入口只作说明，本手册不授予执行权限。实际参数/默认值。

如何实现¶

JobQueue负责排队、领取和状态迁移；Worker负责并发、心跳与回收；handlers把任务交给统一services。来源HTTP、重试、速率与额度通过core组件控制。

为什么这样设计¶

队列把长耗时采集与终端查看分开，错误和部分结果可追溯；额度记账落在source_quota，进程重启不等于预算重新开始。历史claim也不能因为换了worker而复用。

依据：ADR-006、ADR-011、ADR-134。正式迁移/导入完成不表示允许继续采集，当前来源研究结束的边界仍有效。
